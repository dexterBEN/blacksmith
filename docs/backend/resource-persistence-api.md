# Atomic configured Resource persistence

Issue #51 builds on the [configuration v1 contract](resource-configuration-api.md). These operations persist Blacksmith intent only. They never call GCP, reserve a bucket name, check IAM, deploy a service or create deployment status.

## Conditional write

```http
PUT /designs/{designId}/resources/{resourceId}
If-None-Match: *
Content-Type: application/json
```

The caller allocates a nonempty UUID **once per Resource intent**, before sending. DesignId is the existing owner, taken from the path. The Resource ID is globally unique and is never regenerated by this endpoint.

```json
{
  "name": "My storage display label",
  "type": "gcp.storage.bucket",
  "resourceTypeId": "10000000-0000-0000-0000-000000000002",
  "x": 3,
  "y": 2,
  "configuration": {
    "schemaVersion": 1,
    "configuration": {
      "projectId": "example-project-123",
      "bucketName": "blacksmith-example-assets",
      "location": "europe-west9"
    }
  }
}
```

The nested envelope deliberately reuses PR #49's `{schemaVersion,configuration}` format. The issue's flattened example is illustrative and is not accepted. The configuration is stored as a JSON **object** in jsonb, with schemaVersion in its existing separate column.

Rules:

- Exact top-level keys shown above, all required. Unknown/duplicate/case-variant fields, including client Design/Resource overrides and secret-bearing fields, are rejected. Configuration field allowlists and canonical defaults are unchanged from v1.
- Name is a trimmed **display label**, 1–200 UTF-16 code units, independent of bucketName. Neither value proves a cloud resource exists.
- Only exact provider type `gcp.storage.bucket` is supported. The catalog UUID must exist and have code `storage`. On edit, the persisted provider type/catalog must also be compatible. A nullable classification on a legacy bucket can be explicitly classified by this write.
- X is column, Y is row; both are signed 32-bit JSON integers, including negative values. Values outside Int32 or fractional/string values are rejected. There is **no 0–5 limit** and no SQL coordinate CHECK. This preserves historical coordinates and leaves grid growth independent of persistence. The current frontend still has its own 6×6 bounds.
- Maximum request size is 16,384 UTF-8 bytes. The nested v1 envelope retains its depth/strict-key validation. No request JSON logging is added. Field allowlisting is not a general secret detector: resource names/configuration identifiers must be nonsecret.

### Edit and no-op

Read `GET /resources/{resourceId}?include=configuration`. It returns an aggregate representation and a strong ETag such as:

```http
ETag: "resource-11111111111111111111111111111111-r1"
```

Send that exact tag in `If-Match` to the same scoped PUT, with the complete write body. Exactly one supported precondition is required. Wildcard/weak/list edit tags, a tag for a different ID, both preconditions and malformed tags are rejected. Missing precondition returns 428. A valid edit never creates an absent Resource, changes its ID or reassigns its Design. Coordinate/name/configuration edits remain possible subject to occupancy and revision checks.

The Resource revision is a bigint starting at 1, separate from document schemaVersion. A changed configured aggregate advances it once; a semantic no-op at the **current** revision returns unchanged without advancing it. Canonical comparison ignores JSON property order and materializes the existing fixed defaults; a valid historical document can remain physically unchanged on a semantic no-op. Stale tags fail before the no-op check.

`X-Resource-Write-Outcome` reports `created`, `updated` or `unchanged`. Successful PUT returns the canonical aggregate. It does not emit ETag after request normalization; obtain the current validator through GET. New configured timestamps use PostgreSQL microsecond precision so create/read-back values agree.

Conditional create/edit semantics use the standard [If-None-Match / If-Match rules](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1). No generic idempotency platform or operation-history table is added.

## Canonical read-back

```http
GET /resources/{resourceId}?include=configuration
GET /designs/{designId}/resources?include=configuration
```

Aggregate fields: id, designId, resourceTypeId (nullable for legacy rows), name, x, y, type, createdAtUtc, revision, configurationState and configuration. The latter reuses the existing ResourceConfigurationResponse:

```json
{
  "resourceId": "11111111-1111-1111-1111-111111111111",
  "schemaVersion": 1,
  "configuration": {
    "projectId": "example-project-123",
    "bucketName": "blacksmith-example-assets",
    "location": "europe-west9",
    "storageClass": "STANDARD",
    "uniformBucketLevelAccess": true,
    "publicAccessPrevention": "enforced"
  }
}
```

configurationState is `validated`, `absent` or `unsupported`. Absent/unsupported configuration is null; unsupported raw historical JSON is never exposed or defaulted. Metadata/revision remain readable. GET does not write anything. No deployed/saved badge status is invented.

The scoped list loads metadata, configuration and catalog together in one query, ordered by **Y, X, ID**. Each row has its own revision; the list has no whole-Design ETag or cross-request snapshot lock. An unknown owning Design returns 404. Unsupported include values return 400.

Plain existing GET/list DTOs stay unchanged. Existing configuration GET/PUT routes remain available; their response shapes and schema policies are unchanged. schemaVersion 1 still excludes softDeleteRetentionDays and allows only the existing three regions.

## Outcomes and recovery

Application-authored errors use `{ "code": "...", "error": "..." }` on the configured write/conflict paths. Malformed JSON/content types/route syntax retain ASP.NET's standard 400/415/404 responses. Kestrel can produce its normal size-limit response before the action runs.

| Outcome | HTTP / code |
|---|---|
| Conditional creation | 201; created; Location points to aggregate GET |
| Changed existing aggregate | 200; updated |
| Same canonical aggregate at current revision | 200; unchanged; revision retained |
| Existing create ID, including replay | 412 resource_exists; no overwrite |
| Stale edit | 412 revision_conflict; no overwrite |
| Missing precondition | 428 precondition_required |
| Invalid body/precondition/type/catalog association | 400 invalid_payload |
| Missing parent/catalog/edit target | 404 design_not_found / catalog_not_found / resource_not_found |
| Existing target belongs to another Design | 409 resource_design_mismatch |
| Another Resource owns tile | 409 tile_occupied |
| Body too large / exhausted revision | 413 payload_too_large / 409 revision_exhausted |

After a lost/invalid response, GET the **original ID** and compare Design, coordinates, type/catalog, canonical payload and revision. A matching state is recoverable without another create. A mismatch requires deliberate reconciliation. Never allocate a fresh ID or delete a potentially committed Resource to compensate for an uncertain result.

This is recoverable state, **not exactly-once execution**. An immediate 404 does not prove the original operation stopped. No client journal is supplied: a frontend that loses its UUID/intended payload during a crash cannot reconstruct that intent from this backend alone. Replaying create after an explicit deletion can recreate the ID because there are no tombstones. UUIDs must not be reused for another intent; automatic crash retries/delete-resurrection protection remain future work. Design POST remains server-ID/non-idempotent.

## Integrity and legacy clients

Resource and configuration changes commit in **one PostgreSQL transaction**. Failure of either half rolls back both, including revision. Existing-row locks serialize configured/legacy updates; primary-key and tile uniqueness arbitrate concurrent creates whose row does not yet exist.

`UNIQUE (design_id,x,y)` applies to every resource type and every writer. Existing metadata POST still creates a server ID and unconfigured Resource. Legacy metadata PUT still preserves configuration and rejects incompatible type/catalog conversions; metadata and configuration PUTs advance the parent revision. Their DTOs remain unchanged and they remain unconditional/last-write-wins. New conditional clients can detect their intervening edits; legacy clients do not acquire optimistic protection by omitting a precondition. Use the scoped configured PUT for conditional atomic edits.

Legacy POST, metadata moves and ownership changes cannot bypass tile uniqueness: PostgreSQL conflicts are translated to 409 tile_occupied. Deletion locks the Resource, preserves the existing dependent-configuration cascade and does not delete siblings; Design deletion remains restrictive. Direct SQL writers must also maintain revision if participating in this API's conflict protocol.

## Migration and safe local use

Required migration chain includes PR #47's `20261025205111_AddResourceConfigurations`, then **`20261026040000_EnforceResourceIdentityAndOccupancy`**. The latter locks Resource writers, checks duplicate `(design_id,x,y)` groups, and aborts with a diagnostic if any exist. It never deletes or relocates records. Only after preflight does it add revision (existing rows receive 1) and the unique index. Both changes are transactional; no global grid-size constraint is introduced.

On this VM the developer database still has only four older migrations. **Do not run the new backend against it as if its schema were current.** This issue does not migrate it.

A separately authorized operator should:

1. Pause application writers; inspect the target database and migration history.
2. Create a restricted backup **outside Git**, verify its archive listing and test restoration to an isolated database. Never replace the original database as a backup test.
3. Inventory duplicates with `SELECT design_id,x,y,count(*) FROM resources GROUP BY design_id,x,y HAVING count(*)>1;`. Investigate any groups explicitly; never auto-deduplicate. Record existing IDs/coordinates/configuration counts.
4. Using the existing protected connection configuration, run the release's EF migration chain through `20261026040000_EnforceResourceIdentityAndOccupancy` with matching EF Core 8 tooling. Do not put a password in command arguments/logs. If tooling is unavailable, prepare a reviewed migration script from that release in an isolated environment first.
5. Check migration history, original row values, revision backfill, jsonb rows/FKs and the unique index. Verify API health and aggregate read-back before enabling configured writes.

These are instructions for a future approved operation, not commands executed by this PR. A schema rollback removes revision/index, not configuration data, but loses conflict protection. Prefer a compatible application rollback while retaining additive schema and backups; disable conditional writes against an older server. Never roll back PR #47 merely to revert this increment: its Down drops the configuration table.
